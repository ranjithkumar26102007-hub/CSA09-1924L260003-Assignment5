## 1. Scenario Overview and System Sizing

The University Transport Office manages approximately 8,000 active student bus passes annually. Each record must capture the following primary attributes:
1. **Pass ID**: Unique alphanumeric identifier for each bus pass.
2. **Register Number**: Unique student identifier issued by the university.
3. **Student Name**: Full legal name of the student.
4. **Route Number**: University bus route code.
5. **Boarding Stop**: Specific scheduled pickup/drop location.
6. **Validity Date**: Expiration date of the pass.
7. **Amount Paid**: Fee collected for transport services.

### Storage Capacity Estimation
- Average record length in delimited text format: ~58 bytes.
- Total raw data size for 8,000 passes:  
  $$8,000 \times 58 \text{ bytes} \approx 464,000 \text{ bytes} \approx 453.1 \text{ KB}$$
- Sizing consequence: The entire annual pass repository fits well within standard RAM and operating system page caches, meaning sequential scans do not strain disk hardware, but corruptions must be contained strictly at the line boundary.

## 2. Record Layout Specifications

### 2.1 Delimited Text File Layout

In the delimited text format, each record occupies exactly one line, terminated by standard platform line breaks (`\n` or `\r\n`). Fields are separated by the pipe character (`|`).

#### Delimiter Choice Justification
- **Why Pipe (`|`) instead of Comma (`,`)**: Student names frequently include commas (e.g., `Kumar, R.`) and boarding stop descriptions frequently contain commas (e.g., `Poonamallee Bypass, Near Signal`). Using commas requires quote-escaping (`"..."`), which adds complex lexing overhead. The pipe delimiter rarely appears in personal names or location strings, ensuring robust, lightweight splitting.
- **Why Integer Paise instead of Decimal Rupees**: Floating-point representations (`float` or `double`) suffer from IEEE-754 precision inaccuracies during repeated arithmetic. Representing money as integer paise (e.g., ₹4,500.00 stored as `450000`) prevents rounding drift and parsing ambiguity.
- **Why ISO-8601 Date (`YYYY-MM-DD`)**: Lexicographically sortable as plain text, unambiguous across locales, and natively supported by standard date libraries without locale parsing conflicts.

#### Record Layout Table (Delimited Text)
| Field # | Field Name | Data Type | Encoding / Format | Example Value | Validation Rule |
| :---: | :--- | :--- | :--- | :--- | :--- |
| 1 | `passId` | String | UTF-8 Text | `P1001` | Pattern: `^P[0-9]{4,7}$`, Unique |
| 2 | `registerNo` | String | UTF-8 Text | `1924L260003` | Exactly 9 to 11 alphanumeric characters |
| 3 | `name` | String | UTF-8 Text | `R. Ranjith Kumar` | Letters, dots, spaces only; no pipe |
| 4 | `routeNo` | String | UTF-8 Text | `R12` | Pattern: `^R[0-9]{1,3}$` |
| 5 | `boardingStop`| String | UTF-8 Text | `Poonamallee` | Free text; cannot contain pipe delimiter |
| 6 | `validUntil` | String | ISO-8601 Date | `2027-03-31` | Valid calendar date; cannot precede issue date |
| 7 | `amountPaise` | Long | Integer (Paise) | `450000` | Non-negative integer (450000 = ₹4,500.00) |

**Sample Delimited Text Line:**
```text
P1001|1924L260003|R. Ranjith Kumar|R12|Poonamallee|2027-03-31|450000
```

### 2.2 Binary Record Layout using `DataOutputStream`

In binary streams, data is written sequentially in machine-readable byte representation using Java's `java.io.DataOutputStream`. Variable-length strings are written using Modified UTF-8 (`writeUTF()`), where a two-byte unsigned short prefixes the raw string bytes to denote length. Fixed numeric types and dates are written as primitive integer representations.

#### Binary Stream Layout Table
| Order | Stream Write Method | Field Stored | Stored Data Representation | Typical Byte Size |
| :---: | :--- | :--- | :--- | :---: |
| 1 | `writeUTF(passId)` | `passId` | 2-byte length prefix + UTF-8 bytes | $2 + 5 = 7$ bytes |
| 2 | `writeUTF(registerNo)` | `registerNo` | 2-byte length prefix + ASCII bytes | $2 + 10 = 12$ bytes |
| 3 | `writeUTF(name)` | `name` | 2-byte length prefix + UTF-8 bytes | $2 + 15 = 17$ bytes |
| 4 | `writeUTF(routeNo)` | `routeNo` | 2-byte length prefix + UTF-8 bytes | $2 + 3 = 5$ bytes |
| 5 | `writeUTF(boardingStop)`| `boardingStop` | 2-byte length prefix + UTF-8 bytes | $2 + 11 = 13$ bytes |
| 6 | `writeLong(epochDay)` | `validUntil` | 8-byte signed two's complement long (`toEpochDay()`) | 8 bytes |
| 7 | `writeLong(amountPaise)`| `amountPaise`| 8-byte signed two's complement long | 8 bytes |

- **Total Binary Record Size**: Approximately $60 \text{ to } 70 \text{ bytes}$ per record.
- **Trade-off Analysis**: The binary format achieves strict type safety (numeric boundaries are enforced by byte width) and eliminates string-to-number parsing overhead. However, it lacks a human-visible newline separator; a single corrupted byte shifts all downstream offsets.

## 3. Algorithmic Pseudocode (SIMATS Engineering Standard)

### 3.1 Algorithm: Add a Bus Pass

```text
ALGORITHM AddPass
INPUT pass (passId, registerNo, name, routeNo, boardingStop, validUntil, amountPaise), filePath
OUTPUT SUCCESS flag or ERROR description
BEGIN
    1. VALIDATE passId IS NOT EMPTY AND MATCHES FORMAT "^P[0-9]{4,7}$"
    2. VALIDATE registerNo IS NOT EMPTY AND LENGTH >= 9
    3. VALIDATE name IS NOT EMPTY AND CONTAINS NO '|'
    4. VALIDATE boardingStop IS NOT EMPTY AND CONTAINS NO '|'
    5. VALIDATE validUntil IS VALID ISO DATE
    6. VALIDATE amountPaise >= 0
    7. IF ANY VALIDATION FAILS THEN
           RETURN "ERROR: Validation failed for pass fields"
       END IF

    8. line <- passId + "|" + registerNo + "|" + name + "|" + routeNo + "|" + boardingStop + "|" + validUntil + "|" + amountPaise
    9. TRY
           OPEN file AT filePath IN APPEND_MODE
           WRITE line TO file
           WRITE NEWLINE TO file
           FLUSH file buffer
           FORCE synchronization to non-volatile storage
       ON ERROR ioException
           RETURN "ERROR: Write failure during append operation"
       FINALLY
           CLOSE file
       END TRY

    10. RETURN "SUCCESS: Pass record appended safely"
END
```

### 3.2 Algorithm: Find a Pass by ID

```text
ALGORITHM FindPassById
INPUT targetPassId, filePath
OUTPUT matchingPassRecord OR NULL
BEGIN
    1. IF FILE_EXISTS(filePath) IS FALSE THEN
           RAISE EXCEPTION "FileNotFound: The storage file does not exist"
       END IF

    2. OPEN file AT filePath FOR BUFFERED_READING
    3. lineNumber <- 0
    4. foundRecord <- NULL

    5. WHILE HAS_MORE_LINES(file) DO
           line <- READ_LINE(file)
           lineNumber <- lineNumber + 1

           IF IS_BLANK(line) THEN
               CONTINUE
           END IF

           fields <- SPLIT(line, "|")
           IF LENGTH(fields) <> 7 THEN
               LOG_WARNING "Skipping damaged record at line " + lineNumber + ": incorrect column count"
               CONTINUE
           END IF

           TRY
               currentPassId <- fields[0]
               currentAmount <- PARSE_INTEGER(fields[6])
               currentDate   <- PARSE_DATE(fields[5])

               IF currentPassId = targetPassId THEN
                   foundRecord <- CONSTRUCT_RECORD(fields[0], fields[1], fields[2], fields[3], fields[4], fields[5], currentAmount)
                   BREAK
               END IF
           ON ERROR parseException
               LOG_WARNING "Skipping damaged record at line " + lineNumber + ": data conversion error"
               CONTINUE
           END TRY
       END WHILE

    6. CLOSE file
    7. RETURN foundRecord
END
```

### 3.3 Algorithm: List Passes on a Route

```text
ALGORITHM ListPassesOnRoute
INPUT targetRouteNo, filePath
OUTPUT list of matchingPassRecords
BEGIN
    1. IF FILE_EXISTS(filePath) IS FALSE THEN
           RAISE EXCEPTION "FileNotFound: The storage file does not exist"
       END IF

    2. matchingList <- EMPTY_LIST
    3. OPEN file AT filePath FOR BUFFERED_READING
    4. lineNumber <- 0

    5. WHILE HAS_MORE_LINES(file) DO
           line <- READ_LINE(file)
           lineNumber <- lineNumber + 1

           IF IS_BLANK(line) THEN
               CONTINUE
           END IF

           fields <- SPLIT(line, "|")
           IF LENGTH(fields) <> 7 THEN
               LOG_WARNING "Damaged line ignored at line " + lineNumber
               CONTINUE
           END IF

           TRY
               route <- fields[3]
               IF route = targetRouteNo THEN
                   amount <- PARSE_INTEGER(fields[6])
                   passObj <- CONSTRUCT_RECORD(fields[0], fields[1], fields[2], fields[3], fields[4], fields[5], amount)
                   APPEND passObj TO matchingList
               END IF
           ON ERROR parseException
               LOG_WARNING "Skipping corrupt data at line " + lineNumber
               CONTINUE
           END TRY
       END WHILE

    6. CLOSE file
    7. RETURN matchingList
END
```

## 4. Exceptional and Failure Handling Mechanisms

### 4.1 Damaged Line Handling
- **Failure Cause**: Partial write, manual tampering, or unexpected delimiter injection inside a field.
- **Handling Strategy**: When `SPLIT(line, "|")` yields fewer or more than 7 fields, or when numeric conversion (`PARSE_INTEGER`) fails, the parser traps the exception inside the inner reading loop, logs the line number to a diagnostic collector, skips that specific line, and resynchronizes at the next newline character. This guarantees that one damaged row never aborts processing for valid rows.

### 4.2 Missing File Handling
- **Failure Cause**: File not created, path misconfiguration, or accidental deletion.
- **Handling Strategy**: The system strictly checks `FILE_EXISTS(filePath)`. If false, it throws a distinct `FileNotFoundException` rather than returning an empty list or creating an empty dummy file. Treating an absent file as "zero passes" is dangerous because a clerical path typo could falsely convey that no students hold bus passes.

### 4.3 Incomplete Write After Power Failure (Torn Writes)
- **Failure Cause**: System loss of power midway through appending bytes to disk.
- **Handling Strategy**:
  1. *Per-Write Sync*: Every append operation executes `flush()` followed by a low-level file descriptor synchronization (`FileChannel.force(false)` or `FileDescriptor.sync()`), ensuring bytes hit physical storage media.
  2. *Torn Line Containment*: In delimited text, if an interrupted write leaves a truncated line without a terminating newline character, that line will fail the 7-field split or numeric validation and will be skipped cleanly. All prior fully-flushed lines remain 100% valid.

## 5. Architectural Comparison: Delimited Text vs. Fixed-Length `RandomAccessFile`

| Dimension | Delimited Text File (`BufferedReader` / `BufferedWriter`) | Fixed-Length Record (`RandomAccessFile`) |
| :--- | :--- | :--- |
| **Record Access Paradigm** | Sequential line scanning ($O(n)$) | Direct offset seek via calculation: $\text{offset} = k \times \text{recordLength}$ ($O(1)$) |
| **Search by Key** | Linear traversal over all lines ($O(n)$) | $O(n)$ scan, or $O(\log n)$ binary search if keys are sorted |
| **Update in Place** | Impossible; requires reading and rewriting entire file | Directly overwrite record bytes at known seek offset ($O(1)$) |
| **Record Deletion** | Requires full file rewrite ($O(n)$) | Mark record with tombstone/active byte flag ($O(1)$) |
| **Storage Overhead** | Variable length per record (~58 bytes); no wasted padding | Fixed size padded to maximum field lengths (~128 bytes); ~50% waste |
| **Damage Confinement** | **High**: Line break (`\n`) resynchronizes reading loop after a corrupted record | **Catastrophic**: A corrupt length byte shifts subsequent seeks, causing cascading read corruption across all subsequent records |
| **Human Readability** | Editable and inspectable using standard text tools (`cat`, `vim`, notepad) | Opaque binary; requires custom binary hex editor or dedicated tooling |

## 6. Time and Space Complexity Analysis

| Operation | Best Time | Average Time | Worst Time | Auxiliary Space | Complexity Notes |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **Add Pass** | $O(1)$ | $O(1)$ | $O(1)$ | $O(1)$ | Append operation directly writes to end of stream. |
| **Find Pass by ID** | $O(1)$ | $O(n)$ | $O(n)$ | $O(1)$ | Stops immediately when first match is found. Worst-case scans all 8,000 lines. |
| **List by Route** | $O(n)$ | $O(n)$ | $O(n)$ | $O(k)$ | Must exhaust entire file because matching records are distributed across lines. $k$ is number of matches on route. |

- **Space Complexity**: The algorithms run in $O(1)$ auxiliary space during scanning by streaming one line at a time through a small memory buffer (default 8 KB), preventing memory exhaustion even if file size grows.
