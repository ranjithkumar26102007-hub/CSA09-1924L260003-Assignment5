## 1. Scenario: Inter-Wallet Funds Transfer

Consider a campus digital wallet system managing student payments. A student initiates a transfer of **₹500.00** (50,000 paise) from their **Hostel Wallet** (Source: `W_HOSTEL_101`) to the **Campus Canteen Wallet** (Destination: `W_CANTEEN_002`).

### Financial Correctness Constraints
- **Invariant**: The total sum of money across all wallets in the system before the transfer must exactly equal the total sum after the transfer ($\sum \text{Balance}_{\text{before}} = \sum \text{Balance}_{\text{after}}$).
- **The Partial Failure Hazard**: If money is deducted from the hostel wallet, but a server crash, power cut, or database disconnection occurs before the canteen wallet is credited, ₹500 vanishes into thin air.
- **The Concurrency Hazard**: If two debit requests occur simultaneously, both might read an available balance of ₹500 and both proceed to debit ₹500, creating an illegal negative balance (overdraft).

## 2. JDBC Transactional Pseudocode (SIMATS Engineering Standard)

To ensure strict ACID guarantees, JDBC’s default `autoCommit` mode (where each individual SQL statement is committed immediately upon execution) must be disabled.

```text
ALGORITHM TransferWalletFunds
INPUT sourceWalletId, destinationWalletId, transferAmountPaise, dbConnectionSource
OUTPUT SUCCESS or FAILURE_REASON
BEGIN
    1. VALIDATE transferAmountPaise > 0
    2. VALIDATE sourceWalletId <> destinationWalletId
    3. IF VALIDATION FAILS THEN
           RETURN "ERROR: Invalid transfer parameters"
       END IF

    4. connection <- NULL
    5. originalAutoCommit <- TRUE

    6. TRY
           connection <- OPEN_CONNECTION(dbConnectionSource)
           originalAutoCommit <- GET_AUTO_COMMIT(connection)
           
           // STAGE 1: Demarcate Transaction Boundary
           SET_AUTO_COMMIT(connection, FALSE)

           // STAGE 2: Pessimistic Row Lock (Prevent Race Conditions)
           lockSql <- "SELECT balance_paise FROM wallet WHERE wallet_id = ? FOR UPDATE"
           lockStmt <- PREPARE(connection, lockSql)
           SET_PARAMETER(lockStmt, 1, sourceWalletId)
           rsSource <- EXECUTE_QUERY(lockStmt)

           IF NOT HAS_NEXT_ROW(rsSource) THEN
               RAISE EXCEPTION "Source wallet does not exist: " + sourceWalletId
           END IF

           currentBalance <- GET_LONG(rsSource, "balance_paise")
           CLOSE rsSource
           CLOSE lockStmt

           // STAGE 3: Balance Verification
           IF currentBalance < transferAmountPaise THEN
               RAISE EXCEPTION "InsufficientFunds: Available balance " + currentBalance + " < " + transferAmountPaise
           END IF

           // STAGE 4: Debit Source Wallet
           debitSql <- "UPDATE wallet SET balance_paise = balance_paise - ? WHERE wallet_id = ?"
           debitStmt <- PREPARE(connection, debitSql)
           SET_PARAMETER(debitStmt, 1, transferAmountPaise)
           SET_PARAMETER(debitStmt, 2, sourceWalletId)
           debitRows <- EXECUTE_UPDATE(debitStmt)
           CLOSE debitStmt

           IF debitRows <> 1 THEN
               RAISE EXCEPTION "Debit failed: Expected 1 affected row, got " + debitRows
           END IF

           // STAGE 5: Credit Destination Wallet
           creditSql <- "UPDATE wallet SET balance_paise = balance_paise + ? WHERE wallet_id = ?"
           creditStmt <- PREPARE(connection, creditSql)
           SET_PARAMETER(creditStmt, 1, transferAmountPaise)
           SET_PARAMETER(creditStmt, 2, destinationWalletId)
           creditRows <- EXECUTE_UPDATE(creditStmt)
           CLOSE creditStmt

           IF creditRows <> 1 THEN
               RAISE EXCEPTION "Credit failed: Destination wallet not found: " + destinationWalletId
           END IF

           // STAGE 6: Immutable Audit Trail Log
           auditSql <- "INSERT INTO wallet_transfer_log (source_id, dest_id, amount_paise, created_at) VALUES (?, ?, ?, CURRENT_TIMESTAMP)"
           auditStmt <- PREPARE(connection, auditSql)
           SET_PARAMETER(auditStmt, 1, sourceWalletId)
           SET_PARAMETER(auditStmt, 2, destinationWalletId)
           SET_PARAMETER(auditStmt, 3, transferAmountPaise)
           EXECUTE_UPDATE(auditStmt)
           CLOSE auditStmt

           // STAGE 7: Commit All Changes Atomically
           COMMIT_TRANSACTION(connection)
           RETURN "SUCCESS: Funds transferred and transaction committed"

       ON ERROR transactionException
           // STAGE 8: Atomic Rollback on Any Failure
           IF connection IS NOT NULL THEN
               TRY
                   ROLLBACK_TRANSACTION(connection)
                   LOG_WARNING "Transaction aborted. Rollback executed cleanly. Reason: " + transactionException.message
               ON ERROR rollbackException
                   LOG_SEVERE "Critical failure: Rollback failed: " + rollbackException.message
               END TRY
           END IF
           RE_RAISE transactionException

       FINALLY
           // STAGE 9: Clean Resource and State Restoration
           IF connection IS NOT NULL THEN
               TRY
                   SET_AUTO_COMMIT(connection, originalAutoCommit)
               ON ERROR ignored
               END TRY
               CLOSE connection
           END IF
       END TRY
END
```

## 3. ACID Guarantee and Correctness Analysis

The transaction engineering in the above algorithm satisfies all four ACID pillars:

1. **Atomicity ("All or Nothing")**:
   - The debit, credit, and audit log occur within a single atomic transaction block. If an error or system crash occurs after the debit, `ROLLBACK_TRANSACTION` undoes the debit. Neither wallet's balance is modified on disk. Money is neither lost nor magically generated.
2. **Consistency (System Invariants)**:
   - Database level `CHECK (balance_paise >= 0)` constraints and application-level balance validations ensure that negative balances can never be committed. The system transitions strictly from one valid ledger state to another.
3. **Isolation (Concurrency Control)**:
   - By querying with `SELECT ... FOR UPDATE`, the database engine (InnoDB) places a **pessimistic exclusive row lock** on the source wallet record. Any concurrent transfer attempting to read or modify the same source wallet is forced to queue and wait until the current transaction commits or rolls back. This eliminates the classic **check-then-act** race condition.
4. **Durability (Persistence)**:
   - Once `COMMIT_TRANSACTION` returns successfully, the write-ahead transaction log (WAL / Redo Log) is flushed to non-volatile disk. Even if power fails immediately after the method returns, the transaction survives reboot.

## 4. SQL Injection Vulnerability Analysis in Unsafe Login

### 4.1 The Vulnerable String Concatenation Query
Consider the flawed authentication routine:
```java
String sql = "SELECT username, role FROM app_user WHERE username = '" 
             + user + "' AND password = '" + pass + "'";
Statement stmt = connection.createStatement();
ResultSet rs = stmt.executeQuery(sql);
```

### 4.2 Exploitation Mechanics (The Comment-Out Attack)
An attacker inputs the following crafted strings:
- **Username (`user`)**: `admin' -- `
- **Password (`pass`)**: `arbitrary_password`

#### Resulting Raw SQL String Sent to MySQL:
```sql
SELECT username, role FROM app_user WHERE username = 'admin' -- ' AND password = 'arbitrary_password'
```

#### How MySQL Parses This Statement:
1. The SQL parser reads `WHERE username = 'admin'`.
2. The sequence `-- ` (double dash followed by a space) is the standard ANSI SQL comment indicator.
3. The database parser discards everything after `-- ` as a developer comment!
4. The entire password clause: `' AND password = 'arbitrary_password'` is completely erased from the query evaluation tree.
5. The executed logic becomes simply:
   ```sql
   SELECT username, role FROM app_user WHERE username = 'admin'
   ```
6. The query returns the `admin` row with `role = 'ADMIN'`. The attacker logs in with administrative privileges **without ever knowing or supplying the password**.

```
+---------------------------------------------------------------------------------+
| PARSER VIEW OF UNSAFE CONCATENATION                                             |
|                                                                                 |
|  SELECT username, role FROM app_user WHERE username = 'admin' [COMMENT DISCARDED]
|                                                                                 |
|  -> Evaluates TRUE for admin! Access granted without credentials!               |
+---------------------------------------------------------------------------------+
```

## 5. Architectural Defense: Redesign Using `PreparedStatement`

### 5.1 Algorithmic Pseudocode: `SafeLogin` (SIMATS Standard)

```text
ALGORITHM SafeLogin
INPUT inputUsername, inputPassword, dbConnectionSource
OUTPUT userRole OR NULL
BEGIN
    1. VALIDATE inputUsername IS NOT NULL AND inputPassword IS NOT NULL
    2. IF VALIDATION FAILS THEN
           RETURN NULL
       END IF

    3. // SQL query template with parameterized placeholders
       sqlTemplate <- "SELECT username, role, password_hash, salt FROM app_user WHERE username = ?"

    4. TRY
           OPEN connection FROM dbConnectionSource
           // Statement compiled into Abstract Syntax Tree (AST) BEFORE values arrive
           statement <- PREPARE(connection, sqlTemplate)
           
           // Bind parameter strictly as literal data
           SET_PARAMETER(statement, 1, inputUsername)

           resultSet <- EXECUTE_QUERY(statement)

           IF HAS_NEXT_ROW(resultSet) THEN
               storedRole <- GET_STRING(resultSet, "role")
               storedHash <- GET_STRING(resultSet, "password_hash")
               storedSalt <- GET_STRING(resultSet, "salt")

               computedHash <- HASH_PASSWORD(inputPassword, storedSalt)
               IF SECURE_EQUALS(computedHash, storedHash) THEN
                   RETURN storedRole
               ELSE
                   RETURN NULL
               END IF
           ELSE
               RETURN NULL
           END IF

       ON ERROR sqlException
           LOG_ERROR "Authentication error: " + sqlException.message
           RETURN NULL
       FINALLY
           CLOSE resultSet
           CLOSE statement
           CLOSE connection
       END TRY
END
```

### 5.2 Why `PreparedStatement` Completely Eliminates SQL Injection
1. **Compilation Precedes Data Binding**: The database compiler parses the SQL query string into an immutable Abstract Syntax Tree (AST) and compiles an execution plan **before** parameter values are bound.
2. **Type Separation (Code vs. Data)**: When `inputUsername = "admin' -- "` is passed to `SET_PARAMETER(statement, 1, inputUsername)`, the JDBC driver transmits the payload through the binary client-server protocol as pure literal text data.
3. **Immunity to SQL Metacharacters**: Quotes (`'`), dashes (`--`), and semicolons (`;`) inside the data string are treated purely as character literals within the string value. The database checks for a user whose exact username contains the apostrophe and dash characters (`admin' -- `). Because no such username exists in the database, the query safely returns 0 rows.

## 6. Architectural Comparison: Single Transaction vs. Two Auto-Commit Updates

| Evaluation Dimension | Single Transaction (`autoCommit = false`) | Two Independent Auto-Commit Updates |
| :--- | :--- | :--- |
| **Failure Tolerance** | **100% Atomic**: If a crash occurs midway, `ROLLBACK` undoes all prior steps; zero orphan changes remain. | **Catastrophic Failure**: Debit commits immediately; if credit fails, money is destroyed permanently. |
| **Intermediate State Visibility** | **Isolated**: Other database sessions cannot view partial changes (Read Committed / Repeatable Read). | **Dirty/Partial State Visible**: Other users observe the balance drop before the recipient receives funds. |
| **Disk I/O and Flush Overhead** | **1 Disk Flush**: Redo logs are flushed to disk once upon the final `COMMIT`. | **2 Disk Flushes**: Forces a non-volatile synchronous disk flush after every single statement. |
| **Batch Insertion Throughput** | **High Throughput (~5x–10x Faster)**: Network round trips and fsync operations are batched. | **Slow**: Each record incurs separate network round trip and physical disk transaction commit. |
| **Deadlock Vulnerability** | Requires structured resource ordering (`sort by ID`) to avoid cyclic locking. | Rarely deadlocks, but produces corrupt and desynchronized business data. |
| **Coding Complexity** | Requires explicit `try-catch-finally`, rollback logic, and auto-commit restoration. | Trivial single-line statements; no transaction management code. |

### Conclusion
Auto-commit mode is suitable only for single, independent read queries or isolated single-row modifications. Multi-step workflows involving multiple entity updates, financial debits/credits, or batch data ingestion **must always** be enclosed in a managed transaction with explicit `commit()` and `rollback()` handling.
